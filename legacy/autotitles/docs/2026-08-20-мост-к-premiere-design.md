# Спека: Мост к Premiere + каркас приложения

Дата: 2026-08-20
Статус: утверждено пользователем в чате, готово к плану реализации.
Это первая из нескольких подсистем проекта «Варламов Шортс Титры» (см. основной документ [Варламов Шортс Титры.md](Варламов%20Шортс%20Титры.md)). Остальные подсистемы (генератор картинок титров, логика автоподсветки, UI правки, генератор Premiere-скрипта) спроектируются отдельными спеками после этой.

## Цель этой подсистемы

Доказать вживую, что desktop-приложение может: (1) подключиться к запущенному Premiere и читать состояние активной секвенции, (2) получить финальный текст титров без ручного набора в приложении. Это самая рискованная часть всего пайплайна — если мост не работает, дальше делать нечего.

**Definition of done**: приложение запускается, спавнит и подключает `premiere-pro-mcp`, реальным вызовом (не мок-данными) подтверждает, что видит запущенный Premiere и его активную секвенцию, и после drag-and-drop реального .srt-файла показывает распарсенный список реплик (текст + тайминги) в UI.

## Архитектура

Electron-приложение (main + renderer). Main-процесс спавнит `premiere-pro-mcp` (открытый npm-пакет, MIT, Node.js) как дочерний процесс и говорит с ним по MCP-протоколу как клиент — без LLM в рантайме, только типизированные вызовы инструментов (`ping`/`verify_premiere_connection`, `get_active_sequence` и т.д.).

`premiere-pro-mcp` требует свой CEP-коннектор (`.zxp`), установленный в Premiere отдельно — ставится один раз через `premiere-pro-mcp --install-cep`. Приложение должно уметь проверить, установлен ли коннектор, и предложить установку прямо с онбординг-экрана, не отправляя монтажёра в терминал.

## Компоненты

1. **Electron shell** — окно, IPC между main и renderer, упаковка под Windows и Mac (кроссплатформенность — обязательное условие всего проекта, см. основной документ).
2. **MCP-клиент к premiere-pro-mcp** (в main-процессе) — спавн процесса, вызовы инструментов, обработка обрыва соединения.
3. **Онбординг/установка CEP-коннектора** — проверка наличия, кнопка установки, статус.
4. **Парсер .srt** — index / start / end / текст. Обрабатывает BOM, CRLF, многострочные реплики, пустой файл, битый формат построчно (без краша всего файла).
5. **UI (MVP)**:
   - зона drag-and-drop для .srt-файла (монтажёр экспортирует .srt из Premiere вручную и перетаскивает в окно приложения);
   - индикатор статуса подключения к Premiere (подключено / не подключено / коннектор не установлен);
   - после дропа — список распарсенных реплик с текстом и таймингами;
   - справочно — имя и длительность активной секвенции из Premiere (`get_active_sequence`), чтобы монтажёр видел, что мост смотрит в нужный проект.

## Поток данных

1. Запуск приложения → main-процесс спавнит `premiere-pro-mcp`.
2. `ping` / `verify_premiere_connection` → статус в UI: подключено / Premiere не открыт / коннектор не установлен.
3. Если подключено — `get_active_sequence` подтягивает имя и длительность активной секвенции, отображается в UI для сверки.
4. Монтажёр вручную делает Export → Captions/Subtitles в Premiere (получает .srt).
5. Монтажёр перетаскивает .srt в окно приложения.
6. Приложение парсит .srt → список {index, startSeconds, endSeconds, text} → отображает в UI.

## Явно вне скоупа этой подсистемы

- Генерация картинок титров (плашки.py) — следующая подсистема.
- Логика автоподсветки и UI её правки — следующая подсистема.
- Генератор Premiere-скрипта и расстановка на таймлайн (overwrite-редактирование через `premiere-pro-mcp`) — следующая подсистема. Технически уже подтверждено работающим на «Кубе» и «16.08 ЧП», но не входит в эту спеку.
- **MOGRT — не нужен вообще, из скоупа всего проекта убран.** Использовался только в отдельном проекте «Куба» с другим визуальным шаблоном; в пайплайне «Шортс Титры» текст идёт через .srt, а не через MOGRT-параметры.
- Text Animator (переход между соседними плашками) — отдельный открытый технический вопрос (можно ли скриптом запускать его переходы), относится к подсистеме «Генератор Premiere-скрипта», не к мосту.

## Ключевое ограничение и принятый fallback (важно для реализации)

Живое чтение текста из Captions-дорожки Premiere сегодня невозможно ни через классический ExtendScript DOM, ни через QE DOM (оба не видят caption-треки в принципе), ни через `premiere-pro-mcp` (UXP Transcript API, единственный документированный Adobe способ чтения Captions, в пакете смёржен, но не подключён как вызываемый MCP-инструмент — только UXP-протокольные команды без транспорта). Подробности и источники — в разделе «Архитектурный ресёрч 2026-08-20» основного документа.

Поэтому: не строим отдельную UXP-панель ради этого. Текст приходит в приложение через ручной экспорт .srt + drag-and-drop, а не через живой запрос к Premiere.

## Обработка ошибок

- Premiere не запущен / CEP-коннектор не установлен → понятный статус в UI + кнопка/инструкция установки.
- Обрыв соединения с `premiere-pro-mcp` во время работы → статус «отключено», попытка переподключения.
- Битый или пустой .srt → построчная ошибка, не крашит приложение.

## Тестирование

- Юнит-тесты парсера .srt: BOM, CRLF, многострочные реплики, пустой файл, некорректный тайм-код.
- Ручной smoke-тест: открыть реальный проект в Premiere (например «16.08 ЧП»), запустить приложение, убедиться что статус подключения верный и данные активной секвенции совпадают с реальностью; экспортировать .srt и перетащить в приложение, сверить распарсенный список с оригиналом.

## Открытые риски, отложенные на потом (не блокируют эту подсистему)

- Установка CEP-коннектора (.zxp) — разовый шаг для монтажёра, точный UX ещё не проработан (просто инструкция в онбординге vs. попытка автоматизировать вызовом `--install-cep` из приложения).
- Text Animator scripting — нужно проверить отдельно перед проектированием «Генератора Premiere-скрипта».

## Найдено на этапе сборки (2026-08-20): CEP-мост, похоже, обслуживает только одного клиента разом

При попытке смоук-теста (Task 8 плана реализации) параллельно с работающим Claude Code (у которого свой отдельный, уже подключённый MCP-клиент к тому же `premiere-pro-mcp`) — приложение зависло на вызове `ping` и упало по таймауту 60 секунд (`MCP error -32001: Request timed out`), при этом собственная CEP-панель `MCP Bridge` внутри Premiere показывала «Connector running» / всё зелёным, и мой (Claude) параллельный `ping` через уже установленное соединение прошёл мгновенно. Это указывает, что CEP-мост `premiere-pro-mcp` отвечает только одному одновременно подключённому MCP-клиенту — второй независимый процесс (наше приложение) просто не получает ответа, пока слот занят.

Для реального монтажёра это не проблема (он не станет параллельно держать открытым Claude Code с тем же мостом), но это реальное architecture-ограничение, которое стоит держать в голове при любой будущей отладке «почему приложение не подключается» — если рядом одновременно работает Claude Code (или любой другой MCP-клиент) с premiere-pro-mcp, наше приложение не подключится, и это не баг кода.

**Task 8 (сквозная проверка на реальном Premiere) не была доведена до конца в этой сессии** именно по этой причине — отложена: пользователь проверит шаги 3–7 самостоятельно позже, без параллельно открытого Claude Code с premiere-pro-mcp.

## Исправление (2026-08-20, позже в тот же день): гипотеза про «один клиент разом» была неверной

Пользователь проверил Task 8 самостоятельно — гипотеза выше не подтвердилась. Реальных причин оказалось две, обе найдены и исправлены на живом Premiere:

1. **Накопились зависшие процессы `electron.exe`.** Каждый повторный `npm start` (мой и пользователя) оставлял процесс не до конца завершённым — набралось 10 штук, все использующие одну и ту же папку профиля (`userData`), что вызывало ошибки Chromium («Access is denied» на дисковый кэш) и мешало новым запускам. Часть процессов не убивалась даже принудительно (`taskkill` из песочницы агента получал «Access is denied» на дочерние Chromium-процессы) — потребовалась перезагрузка компьютера пользователем.
2. **Настоящий баг в коде, ошибка в исходной спеке Task 3.** `_callTool` парсил `result.content[0].text` и код ожидал внутри поле `.data` (форма `{data: {connected: true, ...}}`). Реальный ответ `premiere-pro-mcp` кладёт эти же данные прямо в `result.structuredContent` — БЕЗ обёртки `.data` в `content[0].text`. Из-за этого `getStatus()` всегда вычислял `pingData` как `undefined` и молча возвращал `connected: false`, даже когда `ping` реально успевал и Premiere отвечал корректно — без единой ошибки, потому что это не бросало исключение, просто неверно читало структуру.

   Источник ошибки: пример формы ответа в брифе Task 3 был скопирован из вывода инструмента `mcp__premiere-pro__ping` **внутри самого Claude** — а это, как оказалось, не сырой ответ MCP-протокола, а обёрнутая Claude Code форма. Разница обнаружилась только когда код заработал с настоящим `@modelcontextprotocol/sdk`-клиентом напрямую (не через Claude), а не в тестах — тесты были написаны по тому же (неверному) примеру из брифа и потому не могли поймать нестыковку.

   **Исправлено:** `_callTool` теперь читает `result.structuredContent` напрямую. Тесты `mcp-client.test.js` переписаны под реальную форму. Проверено вживую отдельным скриптом и через реальный Electron-процесс — `getStatus()` корректно возвращает `connected: true` с именем и длительностью активной секвенции.

**Урок на будущее:** при описании внешнего API в брифе для реализации — использовать пример ответа, снятый с того же самого клиента/протокола, который будет использоваться в реализации, а не с инструмента-обёртки (в данном случае — не с `mcp__premiere-pro__*` внутри Claude, а с прямого вызова `@modelcontextprotocol/sdk`).

## Task 8 закрыт (2026-08-20): мост подтверждён рабочим на реальном Premiere

После фикса выше пользователь перезапустил приложение — статус «Подключено к Premiere», активная секвенция и её длительность отображаются верно. Кнопкой «Обзор…» выбран реальный `.srt` (из проекта «16.08 ЧП»), список реплик с таймингами и текстом корректно распарсен и отображён.

**Drag-and-drop файла из Проводника не работает** — Windows показывает курсор «нельзя» ещё до попытки дропа (значит, ОС/Chromium не считает окно валидной целью; код-уровневые `dragover`/`drop`-обработчики тут ни при чём, отладить удалённо не вышло). **Решение: не чинить, а обойти** — добавлена кнопка «Обзор…» с нативным диалогом выбора файла (`dialog.showOpenDialog`, отфильтровано на `.srt`), которая читает файл в main-процессе и прогоняет через тот же путь `parseSrt` → `renderCaptions`, что и drag-and-drop. Так входная точка есть и работает, drag-and-drop оставлен в коде как есть — при желании можно вернуться к диагностике позже, но сейчас это не блокирует прогресс.

**Definition of done подсистемы «Мост к Premiere + каркас приложения» выполнено.** Следующий шаг — генератор картинок титров (на основе `плашки.py`).
